PUBLIC UPSTREAM SOURCE CORROBORATION

Repository:
  vboxme/Portable-VirtualBox

Source file at observed GitHub revision:
  source/Portable-VirtualBox.au3

The source is AutoIt and requires administrative rights.
It conditionally creates support-driver services based on which driver directory exists.

VBoxDrv route:

  only when <arch>\drivers\VBoxDrv exists
  sc create VBoxDRV ...\drivers\VBoxDrv\VBoxDrv.sys type=kernel start=auto
  sc start VBoxDRV

VBoxSup route:

  only when <arch>\drivers\vboxsup exists
  sc create VBoxSUP ...\drivers\VBoxSup\VBoxSup.sys type=kernel start=auto
  sc start VBoxSUP

The inspected local VirtualBox 7.0.12 payload contains VBoxSup but no VBoxDrv driver payload.
Therefore the payload-side condition that is actually satisfiable is VBoxSup.

The upstream build documentation also states that Portable-VirtualBox is compiled from
Portable-VirtualBox.au3 with AutoIt 3.3.8.1.  This independently agrees with the local
UPX/AutoIt PE evidence and the observed wrapper version surface.

ADJUDICATION

The local failure is not evidence of TempleOSTS guest failure.
The exact support-driver payload exists and is valid, but its Windows kernel-service object
was absent when VirtualBox hardened startup tried to open VBoxDrvStub.

A broad Portable-VirtualBox wrapper launch is NOT selected as the next mutation because the
wrapper source contains additional COM, USB, network, GUI, update, cleanup and launch behavior.
That would exceed the current surgical host-driver intent.
