PREPARATION BINDING

The script does not accept the preparation report as sufficient proof by itself.
It requires:
- no ISO-BOOT-R1-INCOMPLETE.txt.
- report root exact.
- report machine_state poweroff.
- boot order dvd/disk/none/none.
- iso_attached True.
- exact VDI/ISO hash fields.
- STATUS ISO-BOOT-R1-PREPARED.
- manifest path exists and its SHA256 equals the report's manifest SHA256.

The report-supplied current/previous VBOX hashes/file IDs, VDI/ISO file IDs, and isolated-registry SHA256 are then revalidated against the actual files.
VDI and ISO bytes are independently rebound to the fixed authoritative hashes above.

POST-START GATES

On start exit 0:
- showvminfo VMState must be running.
- list runningvms must contain exactly Temple1.10/UUID.
- VBoxSup must remain STATE 4.

The start report binds the runtime-derived preparation-report SHA256 and ISO-boot manifest SHA256.
VBoxHardening.log capture is best-effort and cannot change the actual start verdict if the log is temporarily locked.

No VDI hash-equality requirement is made after start because the guest may legitimately write to the copied VDI during ISO boot/runtime.

VISUAL PROOF BOUNDARY

Host running is not TempleOSTS guest boot proof.
After successful start, a visual screenshot is still required to classify whether the exact ISO reached TempleOSTS desktop/installer/boot failure.
No guest compiler build is authorized merely by host-running state.

FAILURE POLICY

If startvm is issued and fails, or if post-start observation fails:
- the script attempts a distinct start report.
- no retry is issued.
- no poweroff/controlvm rollback is issued.
- actual runtime state is preserved for observation.
